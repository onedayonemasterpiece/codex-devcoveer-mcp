# Промпт исполнителю: операционное качество DevCoveer — реализация и раскатка

Дата постановки: 3 октября 2026. Репозиторий: `onedayonemasterpiece/codex-devcoveer-mcp`.
Инструменты нового окна: GitHub, Codex DevCoveer; OpenCode — в явно описанной ниже роли.

## 1. Поручение владельца и результат

**Выполни реализацию, тестирование, интеграцию и production rollout DevCoveer по этой постановке. Не заканчивай новым аудитом, планом, документацией, открытым PR или сообщением «готово к раскатке».**

Запуск владельцем этого промпта в новом окне является отдельным поручением на реализацию после предыдущего audit-only этапа. В рамках задачи разрешены необходимые изменения исходников DevCoveer, тесты, проверенные коммиты/PR, их слияние по правилам репозитория и штатная раскатка самого DevCoveer. Отдельно разрешены связанные изменения маршрутов документации и статусов обработки IdeaHub. Это не разрешение на массовые изменения/развёртывание остальных продуктов, публикации в социальных сетях или изменение секретов. Обязательные подтверждения платформы и права инструментов сохраняются.

Нужен работающий инструмент, который:

- не теряет всю диагностику из-за одного отсутствующего каталога и не выдаёт неполный поиск за отсутствие ошибок;
- различает основной source, выбранную рабочую копию, установленный runtime и фактически отдаваемые клиенту артефакты;
- направляет ChatGPT и OpenCode к уже существующим решениям и релевантному опыту инцидентов до создания дублирующей реализации;
- показывает межпроектные расхождения и неприменённые исправления общего компонента без нового тяжёлого процесса согласований;
- сохраняет продуктовые требования, полномочия, идемпотентность и восстановление после потерянного ответа.

Здесь исполнительное окно. Независимую приёмку выполняет контрольное окно после получения ссылки на результат. Не выдавай свою самооценку за независимую приёмку и не рассчитывай на автоматическую связь между окнами.

## 4. Способ работы

**Исходники проектируешь и пишешь сам как ChatGPT.** Детерминированные чтения, поиск, изменения, тесты, сборки и Git выполняй через прямые операции DevCoveer/GitHub. OpenCode не используй как замену `git`, тестовому runner или автору всего решения. Native Codex не запускай.

Для проверки реального второго пути контекста разрешена одна короткая read-only задача OpenCode и её продолжение: выбрать подходящие существующие решения и объяснить границы переиспользования без написания кода. Это продуктовая проверка работы контекста агента, а не передача ему разработки. Для непредвиденной операции за пределами типизированных инструментов используй существующий разрешённый operational escape hatch только по реальной необходимости, не для обхода отказа.

Перед записью выбери правильный физический worktree через `find_projects`/`worktree_list`. Сохраняй чужие изменения, не делай reset/clean/stash общего dirty checkout. Используй изоляцию, только когда она нужна; не создавай worktree на каждую мелкую правку. Проверки head/workspace нужны для конкурентной записи в своё дерево, а не как межсервисные зависимости.

Новые операции проводи через существующий `direct_ops_v2` и его `describe`. Не создавай новый набор top-level инструментов без необходимости. Сохрани работающие старые варианты. Если клиентский каталог отстаёт, проверь обновлённую операцию реальным вызовом через уже доступный gateway; не повторяй install/restart ради устаревшей схемы окна. Клиентский отказ, авторизационный отказ и ошибка runtime — разные случаи.

Для долгих команд используй `job_start/job_status`, а для многошаговой работы — существующий work/checkpoint. После потерянного ответа сначала прочитай сохранённую операцию/задачу; не повторяй потенциальный эффект новым способом. Кратко сообщай владельцу уже достигнутые результаты. Не делай искусственную остановку между кодом, тестами, merge и rollout.

## 5. Реализация: границы решения

### А. Правдивая диагностика

Исправь агрегирование ресурсов так, чтобы каждый зарегистрированный корень возвращал собственный результат. Отсутствие/недоступность необязательного корня не скрывает остальные измерения. Права доступа не расширять; не создавать отсутствующий production-каталог только для получения зелёного теста.

Для журналов реализуй ограниченное чтение с продолжением и явным покрытием. У последующих страниц фиксируется та же верхняя граница наблюдения, чтобы новые записи не сдвигали бесконечно конец поиска. Укажи requested/covered interval, retention/rotation gaps, ограничители и способ продолжить чтение. Курсор привяжи к проекту, источнику и параметрам; подмена или истечение должны давать понятную ошибку. Пустой частичный ответ не означает отсутствия совпадений.

У `read_text` различай завершённость порции, запрошенного диапазона и EOF. Возвращай фактический диапазон и продолжение. Точные имена полей выбери совместимыми с текущим контрактом; важно поведение и обратная совместимость.

### Б. Карта существующих решений, работающая в обоих путях

Используй уже заполненный `docs/quality/reuse-catalog.yaml`, а не создавай второй каталог. При обычном входе в project context модель должна видеть компактную карту возможностей и способ раскрыть карточку. В `start_task` и `continue_task` передавай ту же актуальную навигацию и релевантный контекст. Не требуй, чтобы пользователь вручную назвал capability ID.

Семантический выбор делает работающая модель. Детерминированный слой читает/валидирует каталог, разворачивает выбранные ID и проверяет ссылки. Он не должен изображать понимание задачи словарём/регулярками, скрыто вызывать дополнительную LLM или запрещать независимую реализацию из-за похожего имени.

Сохрани различие `shared_library`, `product_service`, `reusable_pattern`, `extraction_candidate`. Полные histories не подставляй по умолчанию. В одном раскрытии — не более пяти развёрнутых карточек; общий byte limit и продолжение явные. Не повторяй полные неизменившиеся карточки при каждом status poll. При недоступности каталога — advisory degradation, не запрет работы и не ослабление Requirements Guard.

### В. Версии, инциденты и контроль расхождений

Добавь компактный inventory: отдельно main/source ref, выбранный checkout, dependency declaration, installed version, served artifact, scope/date последней приёмки. Сведения бери из уже доступных manifests, registered roots, package metadata и release receipts. Не делай широкий поиск секретов или произвольный обход HOME. Неизвестные/недоступные значения сохраняй как unknown с причиной.

Совместимость определяется интерфейсом, версией и нужными capabilities. Digest — целостность артефакта; SHA — воспроизводимость собственного source/deployment. Разные SHA совместимых соседних сервисов не являются ошибкой. Одинаковая версия без нужной capability не является доказательством готовности. Browser/Node/Python-варианты нельзя считать взаимозаменяемыми по старшинству номера.

Свяжи имеющиеся инциденты с общей capability, наблюдавшейся версией, подтверждёнными/предполагаемыми потребителями и исходными доказательствами. Каноническая история остаётся у владельца. Общая модель данных/relations не должна копировать весь журнал в каждый проект. Не объявляй проблему локальных прав общей проблемой WSS.

Реализуй исполняемую проверку межпроектных расхождений через существующий Direct Ops workflow. Она формирует bounded report и diff относительно предыдущего наблюдения: пропущенное исправление, конфликт статуса документации с receipt, несовместимость capability, неполные сведения. Чтение/вычисление и сохранение baseline должны быть честно обозначены по эффектам.

Проверка должна не только существовать как скрипт: подключи её к штатному завершению работы с общей capability/обновлению её receipt или каталога в DevCoveer. Показать срабатывание этого пути на тестовом изменении и получить один реальный портфельный отчёт. Повтор без изменений не создаёт новый инцидент и не повторяет alert. Ошибка advisory-проверки не отменяет уже успешный deploy и не даёт ложного PASS. Не включай новый периодический сервис, внешние уведомления или платные прогоны.

## 6. Definition of Done

Все пункты относятся к этой поставке, а не к будущему roadmap. В отчёте каждому ID сопоставь source/test evidence и, где указан live, фактический вызов установленного инструмента. Один компактный отчёт, не отдельный пакет согласований на каждый пункт.

| ID | Условие приёмки | Необходимая проверка |
|---|---|---|
| D01 | Resources сохраняет достоверные результаты при отсутствии/недоступности одного корня. | Регрессия на missing root и permission failure в контролируемом fixture; после rollout реальный resources не падает целиком. Не удалять production-каталоги для теста. |
| D02 | Поиск по журналу имеет корректное продолжение и правдивое покрытие. | Fixture больше одной страницы с совпадением за первой страницей; чтение до конца без потерь/дублей; rotation/retention gap, invalid cursor и пустой полный интервал. Live: ограниченный последовательный поиск по MCP journal с итоговым coverage, без выдуманного нуля ошибок. |
| D03 | Частичное `read_text` нельзя принять за чтение всего диапазона/файла. | Файл длиннее лимита ответа восстанавливается продолжением без пропусков; EOF и неполный диапазон различимы; legacy-клиент не ломается. Live: чтение длинного безопасного файла через установленный инструмент. |

Состояние baseline сохраняется без новой БД/daemon. |
| D09 | Версии/capabilities не заменены межсервисным SHA-lock. | Контрактные тесты: разные source SHA при совместимом API допустимы; отсутствующая required capability выявляется; неподходящий native/browser transport выявляется; checksum собственного артефакта по-прежнему проверяется там, где требовался. Нет массового обновления consumer dependencies. |
| D10 | Безопасность и восстановление не ухудшены. | Фактический каталог effect annotations проверен; mixed gateway не ложно read-only. Продуктовые сервисы не перезапускаются. |
| D12 | Следующее окно находит изменения и может независимо их принять. | Обновлены существующие canonical docs, описание инструментов/entrypoints и каталог. Статусы OPQ разделяют выполненную часть и backlog. IdeaHub links ведут к существующим принятым документам, selected session validator выполнен; глобальные старые ошибки не объявлены устранёнными. Записан итоговый acceptance report, его ссылка возвращена владельцу. |

Для проверки OpenCode не нужен кодовый агент с правом записи: `provider=opencode`, read-only outcome, короткая задача о выборе существующих компонентов. Никаких публикаций, вызовов Google Live, извлечения секретов или consumer deployment для этого smoke не требуется.

Падение обязательной проверки не обходится переименованием, отключением теста или сменой канала исполнения. Недоступный runner, реальная несовместимость каталога и ошибка реализации учитываются раздельно. Если старые посторонние тесты уже падали, покажи exact-base сравнение; не называй весь набор PASS и не используй это для обхода принятого release gate. Исправляй обнаруженные дефекты в зоне поставки, не перезапускай полный аудит портфеля.

## 7. Интеграция и раскатка без искусственных остановок

Сначала напиши воспроизводящие регрессии и минимальные исправления диагностики. Затем доведи каталог, контекст обеих ветвей, inventory и рабочую проверку расхождений. Общий ограничитель размеров и existing incident/recovery primitives переиспользуй, не размножай helper-файлы.

PR #117 с документацией прими в нужную source-линию штатно после проверки. Реализацию оформи отдельно или в существующей подходящей implementation-ветке; не оставляй владельцу перенос patch руками. PR #91 интегрируй после проверки selected intake и сохранности других сессий. Если main ушёл вперёд, сохрани чужую работу и согласуй изменения обычным Git-процессом, не откатывай main на исторический SHA.

Используй текущую штатную инструкцию build/install DevCoveer и сохранение rollback. Не назначай заранее номер версии без проверки текущей. До единственного необходимого restart сохрани work checkpoint и operation IDs. После restart прочитай фактический installed version, catalogue и результаты D01–D05/D08. Если есть собственная регрессия, выполни штатный rollback и исправление; не оставляй сломанный инструмент под видом завершённого внедрения.

Source/runtime тесты не заменяют клиентскую проверку. Успешный реальный gateway call подтверждает доступность через этот gateway; если для native top-level описания нужно новое клиентское окно, явно оставь именно это внешней контрольной проверкой. Не симулируй fresh-window PASS и не делай повторный deploy только ради client cache.

## 8. Отчёт контрольному окну

Сохрани результат в `docs/reports/operational-quality-phase1-acceptance-20261003.md` на принятой source-линии; достаточно одного отчёта с таблицей D01–D12. Тестовые подробности можно оставить в существующих retained artifacts, в отчёте — конкретные ссылки. Не создавай новый доказательственный framework.

Отчёт содержит:

1. Что изменилось для пользователя и модели: до/после, с примерами реальных кратких ответов инструментов.
2. Таблицу D01–D12: `PASS / FAIL / BLOCKED`, что выполнялось, ref/test/result, дата и граница применимости. Статус независимой проверки отдельно: `awaiting_control_review`.
3. PR/merge, installed version, использованный release source, rollback locator; только несекретные сведения.
4. Точные способы воспроизвести read-only smoke через действующие tools: project, plane, operation, безопасные параметры. Показать реальный маршрут к reuse context и отчёту расхождений.
5. Результат OpenCode smoke и continuation: task ID, использованный контекст и содержательный выбор решений; без raw private transcript.
6. Фактические тесты и ограничения: source suite, live calls, неизменённые старые ошибки IdeaHub, недоступные observability поля, native client-cache check при необходимости.
7. Что не сделано намеренно: OPQ-06/07/09 и невошедшие части OPQ-04/08. Не закрывать весь исходный roadmap.

В финальном сообщении дай ссылку на этот отчёт, состояние поставки и короткое резюме. Если все D01–D12 подтверждены: **`IMPLEMENTED_AND_DEPLOYED — AWAITING_CONTROL_REVIEW`**. Это не независимый PASS. Иначе: **`PARTIAL_DELIVERY`** с точными FAIL/BLOCKED, уже доставленной частью и сохранённым состоянием; не писать «всё готово».

Остановка допустима при реальном внешнем препятствии: отказ полномочий/обязательного подтверждения, недоступный инструмент или release gate, который нельзя удовлетворить в рамках задачи. Сохрани достигнутое, точный неуспешный вызов без секретов, outcome побочного эффекта и безопасный следующий шаг. Не продолжай отклонённое действие другим способом. Обычный объём работы, следующий этап, открытый PR или предстоящее тестирование не являются причиной перекладывать продолжение на владельца.

**Начни с чтения текущих PR/source-контрактов, выбора правильного worktree и воспроизводящих тестов D01–D03. Затем продолжай до работающего развёрнутого результата по D01–D12, а не до следующей постановки.**
