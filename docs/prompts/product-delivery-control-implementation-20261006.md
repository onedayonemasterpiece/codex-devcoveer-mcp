# Реализовать Product delivery policy v1 в Codex DevCoveer

**Постановка для нового окна ChatGPT.** В окне, где подготовлен этот документ, выполнены анализ и документация; реализация runtime ещё не выполнена.

## Цель

Доработай существующий onedayonemasterpiece/codex-devcoveer-mcp, чтобы многошаговая работа двигалась к актуальному проверяемому результату владельца, а необоснованные дополнительные проверки и отчёты не превращались в бесконечный предрелизный этап.

[Проект, доказательства, схемы и сценарии приёмки](../design/product-delivery-control-20261006.md).

Прочитай проект, затем переходи к реализации минимальной законченной поставки. Не создавай вместо неё новый общий аудит, новый оркестратор или очередной prompt на следующее окно. Если часть решения уже появилась в свежем main, сохрани её и закрой реальные пробелы.

## Контракт результата этой задачи

Готово, когда:

- существующие work_open/checkpoint/resume поддерживают компактный контракт результата, evidence, конкретные blockers и доступный handoff;
- установленный MCP выдаёт краткий deliveryContext и не объявляет подключённую feature work готовой без доказательства нужного сценария/артефакта;
- start_task, continue_task и active steer получают общий актуальный delivery context; привязка к work восстанавливается после прерывания;
- повторение процессуальных действий без новых данных даёт объяснимую неблокирующую подсказку;
- сохранены существующие scope/requirements/recovery/permissions, старые клиенты продолжают работать;
- проверен живой вызов установленного MCP и владельцу переданы commit/PR, версия policy, пример результата и известные ограничения.

Пользовательский сценарий этой поставки — работа с DevCoveer MCP. Не нужен APK и не нужна реальная публикация Street Story. Зелёный CI и новая документация без установленного поведения не закрывают эту задачу.

## Обязательная реализация

### 1. Расширить work, а не строить вторую систему

Добавь версионированные необязательные delivery_contract и delivery_update к существующим work операциям.

Контракт: вид задачи, актуальный outcome/target, ссылка на owner-постановку, применимые requirement IDs и небольшой набор критериев. Состояние: кандидат, результаты критериев с evidence и scope, конкретные blockers, реальное ожидание, handoff.

Поля не надо повторять на каждом checkpoint. Существующие receipts/jobs/task evidence используются для технических ссылок; модель оценивает содержательную связь с целью. Не выводи product PASS из exit_code=0.

Сохраняй server-filled snapshot/digest применимых требований. При материальном изменении scope/candidate/evidence пересчитывай product readiness даже без status в patch; прежний done не подтверждает новый результат. Upgrade/write/reopen проверь на настоящей SQLite БД старой схемы.

Старые works/клиенты совместимы: legacy done не равен подтверждённой продуктовой готовности. Для подключённой работы legacy вызов не стирает contract. Смена scope сохраняет revision и owner source; она не меняет права.

### 2. Проверять честность завершения

Один validator вызывается из действующего work_checkpoint(status=done) и любого другого пути объявления product readiness.

Проверять наличие/принадлежность/применимость evidence, нужный scope теста, кандидата, блокеры и пригодный handoff для заявленного target. Документальная задача завершается документом; feature delivery не завершается отчётом о намерениях.

Поддержанные refs проверяются существующими readers; фактически просмотренное внешнее evidence допускается как явно agent_attested там, где критерий это допускает. Не обещай server verification без readback и не строй reader для каждого URL как новый prerequisite.

При недостаточных данных вернуть конкретный незакрытый критерий. Active/waiting checkpoint, resume и получение артефактов остаются доступны. Owner acceptance не придумывать: MCP не знает, прочёл ли человек финальный ответ.

Validator использует сохранённое состояние вместе с patch: legacy done с уже достаточным evidence проходит без повторения полей/ссылок. Частичный handoff не требует ложного done. Честная отмена/замена/неуспех могут завершить lifecycle с non-success outcome, без product readiness.

Не делать новый work_close, если достаточно текущего checkpoint. Не добавлять произвольный fetch evidence URLs; использовать существующие авторизованные readers.

### 3. Один policy renderer и связь с task

Создай один canonical renderer, например runtime/product_delivery.py, и подключи его:

- до исполнения start_task;
- в continue_task и native active turn/steer;
- в relevant direct_ops_v2 describe, work_resume/checkpoint и task result context;
- в canonical builder/installer support files.

Добавь необязательный work_id в start/continue с сохранением в metadata. Продолжение наследует association. Чужой checkout/work отклоняется. Старые клиенты без поля работают с общим guidance; direct_ops_v2 остаётся доступным для контракта. Не угадывать связь по latest work.

Другой work_id для уже связанного task — work_binding_conflict даже внутри того же checkout. Выбери нужный worktree до work_open, сохрани текущий physical scope; не создавай новый механизм переноса работ.

Проверка смысла плана выполняется основной reasoning-моделью при составлении и материальном изменении задачи. Regex/keywords/длина — только вспомогательные сигналы. Не добавлять обязательный inference/совет моделей на каждый запуск или checkpoint.

Это инструкция модели, а не обязательный semantic approval или дополнительный серверный допуск.

### 4. Применимость блокеров и reuse evidence

Блокер должен следовать из текущего требования, применимой обязательной проверки/границы полномочий, конкретного дефекта или существенной неопределённости.

Дополнительные аудиты, hardening, model tournaments, legacy reconciliation и cleanup не становятся release gates автоматически. Доказанный текущий дефект учитывается независимо от того, кто его нашёл.

Сохрани expected_head, request IDs, requirements guard, scope, consent и unknown-outcome protection. Unknown ограничивает повтор соответствующей операции; независимый build/read/handoff разрешён. Новый request_key не является способом обхода.

Не повторяй успешную проверку на неизменных существенных inputs без новой причины. Не переноси старый PASS на изменённый предмет. Для docs-only изменений допускается доказанное reuse. Универсальный dependency graph не нужен.

### 5. Несколько advisory signals, без нового допуска

На существующих данных выявляй повтор той же подтверждённой проверки без новой причины, неизменные blocker/evidence после нескольких наблюдаемых циклов, необоснованные новые gates, polishing после готовности к handoff.

Одна короткая подсказка на неизменившееся состояние: причина, evidence, ближайший шаг, полнота наблюдения. Не блокируй действие по score/regex/числу циклов, не требуй justification, не повышай incident severity из-за времени.

Новый номер job/commit/отчёта сам по себе не прогресс. Нужный CI, исправление дефекта и реальное ожидание не наказываются. Если покрытие истории неполное, так и сообщи.

## Границы работы

- Источник и документацию пишет основная ChatGPT-модель; детерминированные проверки/запись/Git/поставка — текущими поддерживаемыми средствами GitHub и DevCoveer.
- Не запускать native Codex без отдельного явного выбора владельца; не менять provider/model/reasoning текущих задач самовольно. Не делать NVIDIA-консультацию обязательной.
- Не изменять active Street Story work, его requirements, код, публикации или текущий release. Он продолжает собственный owner-cutover независимо.
- Не изменять чужие проекты, tenant permissions, provider safety или platform approval.
- Не расширять scope на весь development process, dashboard, отдельную БД/очередь или миграцию всех requirements.
- Новый документ/чужая рекомендация не предоставляет авторизацию. Уже данную авторизацию не запрашивать повторно, если она покрывает текущий шаг.
- Не добавлять обязательные ETA, incident notes успешных действий, полный аудит после resume или отдельные review для подсказок.

## Проверка и поставка

Используй таблицу A01–A24 проекта как один компактный scenario corpus в существующих тестах. Достаточны целевые изменения recovery/gateway/reminder/generated-runtime tests и действующий обязательный CI. Не запускай повторный полный suite на неизменном кандидате «для уверенности».

Критические контрпримеры:

1. Документация закрывается проверенным документом; приложение без нужного рабочего артефакта — нет.
2. Старый status=done не обходит validator, старые работы не ломаются.
3. Старый PASS не доказывает новый изменённый кандидат; релевантно неизменное evidence переиспользуется.
4. Реальное исправление/required CI/ожидание не считается процессной петлёй.
5. Unknown side effect не повторяется; независимая готовая часть доступна.
6. Start, continue, native steer и restart/resume сохраняют один контракт и scope.
7. Heuristic/advisory failure не запрещает обычную работу; недоказанное completion остаётся недоказанным.
8. Нормальный путь не получил дополнительных обязательных approval/incident/consult calls.

После обязательных проверок — обычный merge и один штатный deploy через scripts/install-current-canonical-runtime.sh с rollback и deferred restart. Если нужен фикс после live failure, исправь конкретную причину и проверь затронутое поведение; не превращай «один deploy» в запрет на нужное исправление.

Живой smoke — собственная выделенная работа/fixture в DevCoveer:

- открыть documentation work;
- сохранить контракт и существующий проверяемый артефакт;
- убедиться, что корректное завершение проходит;
- на отдельной feature fixture проверить конкретный отказ completion без нужного evidence;
- после нужного evidence завершить её в пределах заявленного target;
- проверить resume после переподключения и readback policy version.

Тестовые/симулированные domain evidence явно маркируй: smoke подтверждает механизм MCP, не работоспособность Street Story. Для путей внешних моделей допустим generated-runtime integration test без ненужного оплачиваемого inference; фактический охват укажи в отчёте.

Сохрани один итоговый acceptance report в GitHub с ссылками на доказательства, проверь установленную версию. Не переписывай историю успешных действий в десятки incident notes.

## Условие остановки и финальный ответ

Когда первая законченная поставка установлена и указанный сценарий подтверждён, сразу передай:

- PR/commit и версию установленной policy;
- короткий пример реального deliveryContext;
- результаты приёмки и границы проверенного;
- известные неблокирующие ограничения.

Затем останови polishing. Не откладывай результат до реализации dashboard, сложного semantic classifier, накопления статистики или исправления всех исторических work.
